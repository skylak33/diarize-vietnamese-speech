# Отчёт и план дальнейшего анализа диаризации

## 1. Цель следующего этапа

Следующий этап должен определить причины оставшихся ошибок до перехода к PLDA,
дообучению ECAPA или изменению production-конфигурации. Анализ необходимо вести
в трёх независимых направлениях:

1. качество и область действия эталонной разметки;
2. ошибки определения количества спикеров и временного назначения кластеров;
3. калибровка AHC и centroid merge на отдельном development set.

Текущая конфигурация остаётся экспериментальным кандидатом:

```yaml
embedding:
  window_sec: 1.5
  step_sec: 0.75

vad:
  threshold: 0.5
  min_silence_ms: 200

clustering:
  method: ahc
  threshold: 0.75

postprocessing:
  centroid_merge:
    enabled: false
```

Она не должна становиться окончательным production default до независимой
валидации.

## 2. Подтверждённые результаты

### 2.1. Качество reference-разметки

Ручное прослушивание подтвердило неполную разметку трёх записей:

| Запись | Подтверждённое содержание до начала reference |
| --- | --- |
| `C4HFERLpRfI` | Спикер 1 с 0:00, спикер 2 с 0:12, смех спикера 1 около 0:44, спикер 2 около 0:45. |
| `Uaq5N3FbQb4` | Спикер 1 с 0:00 на фоне музыки, спикер 2 примерно с 0:36. |
| `ed0Vt0NxJUI` | Спикер 1 с 0:00, спикер 2 с 0:09. |

В текущем reference у каждой записи указан один спикер, а речь размечена только
в поздней части аудио. Эти три файла дают 114.310 из 218.273 секунд FalseAlarm,
то есть 52.37% всего FalseAlarm корпуса, при наличии только 28.226 зачтённых
reference speaker-seconds.

Вывод: их текущие DER, FalseAlarm и классификация speaker count недостоверны для
оценки всего аудио. Приблизительные точки смены спикеров нельзя использовать для
автоматического исправления RTTM.

### 2.2. Источники SpeakerError

На полном наборе из 100 записей получено:

| Группа | Файлов | SpeakerError, с | SpeakerError rate |
| --- | ---: | ---: | ---: |
| Верное количество спикеров | 60 | 72.322 | 2.68% |
| Неверное количество спикеров | 40 | 326.930 | 18.89% |
| Overcount | 26 | 132.389 | 12.48% |
| Undercount | 14 | 194.540 | 29.07% |

После исключения трёх файлов с подтверждённо недостоверным speaker count:

| Группа, диагностические 97 файлов | Файлов | SpeakerError, с | SpeakerError rate |
| --- | ---: | ---: | ---: |
| Верное количество спикеров | 60 | 72.322 | 2.68% |
| Неверное количество спикеров | 37 | 326.765 | 19.20% |
| Overcount | 23 | 132.224 | 12.80% |
| Undercount | 14 | 194.540 | 29.07% |

Основная часть SpeakerError связана с неверным количеством кластеров. Самая
тяжёлая группа — undercount. При этом остаётся отдельный класс временных ошибок
при правильном количестве спикеров. Первые кандидаты для прослушивания:

- `98EV6H0ZRlU`: 15.312 секунды SpeakerError;
- `B5rLHPUJ8qc`: 11.810 секунды;
- `jxTaydBnwIg`: 9.000 секунд;
- `XSC94UbpoRQ`: 7.250 секунды.

### 2.3. Centroid merge

Для порогов 0.75, 0.80 и 0.85 результат одинаков:

- 84 попытки объединения;
- 0 принятых и 84 отклонённых;
- максимальная лучшая cosine similarity — 0.534;
- средняя лучшая similarity — 0.293, медиана — 0.312;
- все 84 кандидата отклонены по similarity threshold;
- у 17 кандидатов дополнительно не выполнен minimum margin.

Centroid merge не сломан: его пороги не соответствуют наблюдаемому диапазону
similarity. Снижать threshold примерно до 0.5 без development-разметки нельзя:
это создаст несколько объединений, но не докажет, что они корректны.

### 2.4. Кэш эмбеддингов

Кэш работает и сохраняет результат диаризации неизменным. На полном корпусе
первичное извлечение заняло 122.45 секунды, а совместимые повторные конфигурации
с 100 cache hits выполнялись за 1.74–1.83 секунды. Кэш можно использовать для
AHC sweep, если VAD, окно, checkpoint, encoder, device и seed не меняются.

## 3. План действий

### Этап A — определить корректную область оценки

1. Проверить документацию и источник ViYT-Diar: должна ли разметка покрывать всё
   аудио или только заданные области.
2. Если ожидается полное покрытие, создать точный RTTM для трёх проблемных
   записей: границы начала и конца каждого речевого сегмента, speaker label,
   паузы, смех и пересечения.
3. Если размечается только часть аудио, получить официальный UEM. Не выводить
   UEM из ошибок системы и не выбирать области после просмотра DER.
4. Провести вторую ручную проверку исправленных RTTM/UEM.
5. Только после этого пересчитать corpus DER и покомпонентные ошибки.

Результат этапа: документированная область scoring и валидные reference-файлы.

### Этап B — классифицировать оставшийся SpeakerError

Для каждой записи сохранить одну из причин:

- `overcount`: лишние кластеры одного реального спикера;
- `undercount`: объединены разные реальные спикеры;
- `correct_count_assignment`: количество верное, но интервалы назначены неверно;
- `boundary_or_vad`: ошибка в основном вызвана границей речи, пропуском или FA;
- `reference_issue`: обнаружена дополнительная проблема эталона.

Порядок разбора:

1. четыре записи с наибольшим SpeakerError при правильном количестве;
2. все 14 undercount-записей;
3. overcount-записи по убыванию SpeakerError;
4. оставшиеся случаи.

Для временных ошибок сравнить reference и hypothesis на единой временной шкале.
Отдельно отметить смешанные embedding-окна около быстрых смен спикеров, длинные
ошибочные участки одного label и локальные ошибки VAD.

Результат этапа: таблица `recording_id -> категория -> длительность ошибки ->
наблюдение`, а также суммарные секунды и доля SpeakerError по каждой причине.

### Этап C — выполнить AHC sweep на development set

Development set должен быть отделён от использованного test set и включать
разные количества спикеров, фоновые условия и длительности. На нём выполнить
один фиксированный sweep:

```powershell
python -m experiments.run_diarization_experiments `
  --audio_dir <development-audio> `
  --ref_rttm_dir <development-reference-rttm> `
  --model exps/exp1/model/model_0034.model `
  --output_dir results/dev_ahc_stability `
  --experiment ahc_stability `
  --vad_min_silence_ms 200 `
  --window_sec 1.5 `
  --device cuda `
  --seed 42 `
  --collar 0.25
```

Сравнить пороги `0.70`, `0.72`, `0.74`, `0.75`, `0.77` по следующим метрикам:

- DER, Miss, FalseAlarm и SpeakerError;
- count accuracy и MAE количества спикеров;
- доля overcount и undercount;
- результаты отдельно по числу reference-спикеров.

Выбрать порог по минимальному DER при контролируемом балансе overcount и
undercount. После выбора порог зафиксировать и больше не настраивать на test set.

### Этап D — принять решение по centroid merge

Centroid merge оставить выключенным во время основного AHC sweep. После выбора
AHC threshold на development set можно отдельно проверить несколько реально
наблюдаемых порогов ниже 0.534. Любое объединение должно оцениваться по изменению
DER и count error, а не только по cosine similarity.

Критерий включения: устойчивое улучшение на development set без роста
undercount. Если такого улучшения нет, удалить centroid merge из активного
экспериментального плана и сохранить только диагностическую статистику.

### Этап E — независимая итоговая оценка

После исправления reference-протокола и выбора AHC threshold выполнить ровно
один запуск на новом, ранее не использовавшемся test set. В итоговом отчёте
сохранить конфигурацию, checkpoint hash, seed, состав development/test sets и
все компоненты DER.

## 4. Критерии перехода к более сложным моделям

PLDA или fine-tuning ECAPA следует рассматривать только если одновременно:

1. reference/UEM проверены;
2. AHC sweep выполнен на независимом development set;
3. основные ошибки остаются speaker-confusion, а не VAD или границы;
4. ошибки нельзя объяснить неверным количеством кластеров или смешанными окнами;
5. имеется отдельный test set для оценки следующего изменения.

До выполнения этих условий PLDA и fine-tuning смешают ошибки данных, scoring и
кластеризации и не дадут интерпретируемого результата.

## 5. Запрещённые сокращения эксперимента

- не считать 97-файловый subset исправленным benchmark;
- не удалять три проблемные записи ради снижения DER;
- не создавать RTTM из приблизительных точек ручного прослушивания;
- не подбирать UEM по hypothesis или величине ошибки;
- не выбирать AHC threshold на старом test set;
- не включать centroid merge только потому, что более низкий threshold создаёт
  объединения.

## 6. Ближайший практический результат

Первым артефактом должна стать проверенная полная разметка или официальный UEM
для `C4HFERLpRfI`, `Uaq5N3FbQb4` и `ed0Vt0NxJUI`. Параллельно можно прослушать
четыре записи с правильным speaker count и максимальным SpeakerError, поскольку
эта работа не зависит от выбора нового clustering threshold.
